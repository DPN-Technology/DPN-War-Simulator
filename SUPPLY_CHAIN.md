# Software Supply Chain

DPN Technology maintains machine-readable and human-readable dependency records for each published release.

## Release Inventory

The `Supply Chain` workflow always inventories the **immutable release tag**, not the moving `main` branch.

Each current release receives:

- `SBOM.spdx.json` — SPDX JSON SBOM generated by Anchore Syft
- `SBOM.cyclonedx.json` — CycloneDX JSON SBOM generated by Anchore Syft
- `SBOM_SHA256SUMS.txt` — SHA-256 hashes for both SBOM documents
- `SBOM_MANIFEST.txt` — repository, release tag, source commit, scanner version, and generation time
- `SOURCE_SHA256SUMS.txt` — SHA-256 hashes for tracked release-source files
- `DEPENDENCY_INVENTORY.txt` — readable declared-dependency inventory

The SPDX step also submits a dependency snapshot to GitHub's dependency graph.

## Scanner Reproducibility

The workflow pins:

- `anchore/sbom-action@v0.24.2`
- Anchore Syft `v1.51.0`

This prevents an unreviewed scanner-version change from silently altering a release inventory.

## Verification

Verify the two SBOM documents:

```bash
sha256sum -c SBOM_SHA256SUMS.txt
```

Verify tracked source files from a checkout of the tagged release:

```bash
sha256sum -c SOURCE_SHA256SUMS.txt
```

The source ZIP generated by the Release workflow has its own `SHA256SUMS.txt`.

## Release Traceability

The intended chain is:

```text
CI / Tests
   ↓
Immutable Git Tag
   ↓
GitHub Release
   ↓
Source ZIP + SHA-256
   ↓
Exact Tag Checkout
   ↓
SPDX + CycloneDX SBOMs
   ↓
Source Hashes + Dependency Inventory
```

## Inventory Scope

The DPN dependency inventory searches declared dependencies from common repository manifests including Python requirements, Node package manifests, Gradle/Maven coordinates, Docker base images, and GitHub Actions references.

Runtime plugins, operating-system packages, externally installed AI models, infrastructure dependencies, and services not declared in the repository can require a separate operational inventory.

## Security

SBOM and inventory files must never contain production passwords, tokens, API keys, private keys, live databases, backups, employee/customer data, or private operational exports.

GitHub artifact attestations can be added later if the repository/account plan supports attestations for private repositories.
